# 提交规范

这个仓库放着三个应用，提交记录一乱，GitHub 上每个目录的「Last commit message」就会挂上别的应用的说法——看起来就像内容串了。以下规则是为了避免这件事。

## 格式

```
<type>(<scope>): <一句话说明>
```

**type**

| 类型 | 用在 |
|---|---|
| `feat` | 新功能 |
| `fix` | 修 bug |
| `refactor` | 重构，行为不变 |
| `docs` | 文档 |
| `chore` | 构建、依赖、杂务 |
| `style` | 格式，不影响逻辑 |

**scope**

| scope | 范围 |
|---|---|
| `calendar` | 日历倒计时应用 |
| `music` | 音乐应用 |
| `gately` | Gately 网关应用 |
| `repo` | 仓库级：根 README、LICENSE、`.gitignore`、`docs/` |
| `deps` | 依赖升级 |

## 三条硬规则

**1. 一个提交只动一个应用**

跨应用的需求（比如「三个应用版本号都对齐到 3.0.0」）拆成 N 个提交，各写各的版本号。理由很实际：GitHub 文件列表显示的「Last commit message」是**最后一次改动该文件的提交**，一个提交里混了两个应用，其中一个应用的文件就会显示成另一个应用的说明。

**2. 无关改动不要单独成一条**

改个 LICENSE 标题、修个链接、调一下措辞——这类改动合进相关的那次提交里，不要单独开一笔。仓库历史应该读起来像「做了什么功能」，而不是「今天改了几处文案」。

反例：

```
feat(gately): 异常优先展示 1.3.0
docs: 许可证标题覆盖三个微应用      ← 应该合进上一条
```

正例：

```
feat(gately): 异常优先展示 1.3.0
```

（LICENSE 的改动放在同一个提交里，或者在提交信息末尾补一句说明。）

**3. 描述写「做了什么」，不写「改了哪个文件」**

```
✗ update README.md
✗ fix bug
✓ docs(repo): 根 README 只保留索引，各应用细节移到各自目录
✓ fix(gately): 切换服务器后证书页仍显示上一台的数据
```

## 正文什么时候写

改动涉及三个文件以上、或者有「为什么这么改」需要解释时，空一行写正文。用短横线列要点，一条一行。

```
feat(gately): 1.1.0 支持多台服务器

- 设置页改为服务器清单，逐台测试权限、设默认
- 卡片绑定一台，标题改用用户起的名字
- 主窗口顶部加切换条，每台独立轮询与缓存
- 旧版单实例配置自动迁移
```

## 合并前自查

```bash
git log --oneline -5                    # 最近五条读起来顺不顺
git show --stat HEAD                    # 这一笔是不是只动了一个应用
git log --oneline origin/main..HEAD     # 待推的有几条，能不能合并
```

如果 `git show --stat` 里出现了两个应用目录，就该拆开。
